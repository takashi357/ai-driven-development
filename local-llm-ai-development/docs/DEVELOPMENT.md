# 開発記録：診断の設計を見直した経緯

記録日：2026年9月20日。開発時のAIコーディング支援とのやり取りとGit履歴を要約したものです。やり取りの全文と初期版の全差分は、このリポジトリには含めていません。

## 最初の要件

日本の一般利用者と小規模事業者に向けて、PCのRAM、主な用途、情報の扱い方、速度と品質の優先度から、現実的なローカルLLMの使い方を示すサイトを作ることから始めました。

要件として、次の3点を定めました。

- 公式に確認できた仕様と、用途への適性の推定を区別する。
- 実際に選択を変えて、結果が変わることを確かめる。
- Web版の閲覧範囲を、当初に決めた範囲から広げない。

## 初期版の問題

初期版は2×6×3×3＝108通りの入力を扱い、入力を変えると文面が更新されることを確認していました。しかし、16GBの54条件中39条件で、4B級を出発点にする設計になっていました。

私が実際に操作すると、さまざまな条件を指定しても同じ答えが返るように見えました。選択操作が成立することや文章に差分が出ることだけでは、「その選択が意思決定に役立つか」という品質を十分に検証できていなかったのです。

## 指摘に基づく修正

私は、6B・7B級も比較対象になるのではないかと考え、診断の設計を見直しました。モデル規模の表示に加えて、「ローカルで試す」「送信できる情報はクラウドと比較する」「品質が足りない部分は人に戻す」「最新情報の取得を先に行う」といった作業方針を先に示す設計に変えています。

モデルの比較範囲は、用途・RAM・速度と品質の優先度に応じて変わります。一方、情報を外部へ送れるかどうかを変えただけで、必要なモデル規模まで機械的に変えることはしません。

6B級と7B級の実在する候補には、配布容量や対応言語の公式情報を添えました。あわせて、配布容量とPC全体の必要RAMは別物であること、日本語への適性やモデル世代間の優劣は別途検証が必要であることも画面に表示しています。

## 検証に追加した観点

| 条件の変更 | 確かめること |
|---|---|
| 16GBで、下書きから要約へ | モデルの比較範囲が2〜4B級から4〜7B級へ変わる |
| 速度から品質へ | 小型から7〜9B級の条件付き比較へ変わる |
| 外部送信不可から公開情報中心へ | 作業方針は変わる。メモリ要件を理由なく変えない |
| 用途を最新情報の調査へ | ローカルLLM単体での確認を対象外として扱う |
| 8GBで外部送信不可・品質優先 | 品質不足時の受け皿として、人の対応を残す |

これらは、アプリで採用した判断ルールが意図どおりに動くかの検証です。

## 使われていないPCの再利用への発展

次に、8GBのPCで準備し、16GBのPCで活用するような分担ができるかを検討しました。官公庁や中小企業などで使われていない端末を再利用する、という想定です。

実装した分担は次のとおりです。

1. 準備担当がテキストと資料名・目的を入力する。
2. ブラウザー内で文字数を基準に分割し、JSONを書き出す。
3. 組織で認められた方法で、活用担当へファイルを渡す。
4. 別のブラウザーでJSONを読み込み、仕事とブロックを選ぶ。
5. 作成した指示文を、別途導入したローカルLLMで実行する。
6. 人が回答を原文と照合する。

このうち1、2、4と指示文の生成が、このアプリの機能です。端末間の自動転送、モデルのインストール、AI推論、回答の自動採用は実装していません。

## 役割分担

| 担当 | 開発中の役割 |
|---|---|
| 私 | 目的と対象者の設定、診断の偏りの発見、6B・7B級の比較と8GB→16GBの分担の提案、採用する方向の決定 |
| AIコーディング支援 | 公式資料の確認、画面とロジックの実装、操作検証の実行、修正、オフライン版の生成、開発時のWeb版への反映 |
| 実際に運用する組織 | 端末・モデル・情報の利用可否、業務品質、運用コストの判断（開発時点では未実施） |

## この記録から得られたこと

操作できる試作品を早く用意すると、使う立場から具体的な違和感を指摘できます。その違和感を、変更する仕様と検証する条件に落とし込んだことが、この改善につながりました。

GitHub版には、現在の実装を1つのスナップショットとして収録しています。開発時のWeb版のGit履歴は含めていません。

## GitHub掲載版での検証スクリプトの修正（2026年9月20日）

2026年9月20日、GitHub掲載版の検証スクリプトを再実行したところ、`tests/diagnosis.cjs`で`TypeError: path.join is not a function`が発生しました。HTTPリクエストのパス文字列を`path`という変数名にしていたため、Node.jsの`path`モジュールと名前が衝突していたことが原因です。

文字列の変数名を`pathname`へ変更し、診断・受け渡し・オフライン版の3スクリプトを再実行しました。このエラーは、AIコーディング支援で検証スクリプトを再実行した際に検出されたテスト用コードの不具合で、修正もAIコーディング支援で行いました。アプリ本体の診断ルールは変更していません。結果と実行環境は[検証記録](VERIFICATION.md)に記載しています。

## 前提と限界

- 上記の検証は判断ルールの検証で、モデルの実測結果ではありません。
- 使われていないPCの台数や配備状況は調査していません。
- 開発時間の削減率や、AIを使わない開発との生産性の比較は測定していません。また、モデル推論の品質や、使われていないPCでの効果を実証した事例でもありません。
