# AIとの対話から、診断の設計を見直した記録

記録日：2026年9月20日。開発時に整理された対話・Git履歴の要約です。以下の「利用者」は依頼者の樋口隆史を指します。会話の全文・初期版の全差分は、このリポジトリには同梱していません。

## 最初の依頼

日本の一般利用者と小規模事業者に向けて、PCのRAM、主な用途、情報の扱い方、速度と品質の優先度から、現実的なローカルLLMの使い方を示すサイトを作る依頼から始まりました。

公式に確認できた仕様と、用途への適性の推定を区別すること、実際に選択して結果が変わることを確かめること、Web版の公開範囲を勝手に広げないことが条件でした。

## 初期版で取りこぼしたこと

初期版は2×6×3×3＝108通りの入力を扱い、入力変更による文面の更新を確認しました。しかし、16GBの54条件中39条件が4B級を出発点にする設計でした。

利用者には、さまざまな条件を指定しても同じ答えが返るように見えました。選択操作の成立や文章の差分だけでは、「その選択が意思決定に役立つか」という品質を十分に検証できていませんでした。

## 指摘を受けた修正

利用者から、6B・7Bあたりも比較対象になるのではないか、という指摘がありました。そこで、モデル規模の表示に加えて、先に「ローカルで試す」「送信できる情報はクラウドと比較する」「品質不足は人に戻す」「最新情報の取得を先に行う」といった作業方針を出す設計に変えました。

モデルの比較範囲は、用途・RAM・速度と品質の優先度に応じて変わります。一方、情報を外部へ送れるかどうかを変えただけで、必要なモデル規模まで機械的に変えることはしません。

6B級と7B級の実在する候補について、配布容量や対応言語の公式情報を添えました。配布容量をPC全体の必要RAMと混同しないこと、日本語への適性やモデル世代間の優劣は別に検証が必要であることも表示しています。

## 検証で追加した問い

| 条件の変更 | 確かめること |
|---|---|
| 16GBで、下書きから要約へ | モデルの比較範囲が2〜4B級から4〜7B級へ変わる |
| 速度から品質へ | 小型から7〜9B級の条件付き比較へ変わる |
| 外部送信不可から公開情報中心へ | 作業方針は変わる。メモリ要件を理由なく変えない |
| 用途を最新情報の調査へ | ローカルLLM単体での確認を対象外として扱う |
| 8GBで外部送信不可・品質優先 | 品質不足時の受け皿として、人の対応を残す |

これらは製品内で採用した判断ルールの検証です。モデルの実測結果を示すものではありません。

## 休眠PCの再利用への発展

次の問いは、8GBで準備し、16GBで活用するような分担ができるか、というものでした。官公庁や中小企業の未活用端末を再利用する方向へ、目的が具体化しました。未活用PCの台数や配備状況を調査・確認したという意味ではありません。

実装した分担は次の通りです。

1. 準備担当がテキストと資料名・目的を入力する。
2. ブラウザー内で文字数を基準に分割し、JSONを書き出す。
3. 組織で認められた方法で、活用担当へファイルを渡す。
4. 別のブラウザーでJSONを読み込み、仕事とブロックを選ぶ。
5. 作成した指示文を、別途導入したローカルLLMで実行する。
6. 人が回答を原文と照合する。

このうち1、2、4と指示文の生成が本アプリの機能です。端末間の自動転送、モデルのインストール、AI推論、回答の自動採用は実装していません。

## 人とAIが担ったこと

| 担当 | 開発中の役割 |
|---|---|
| 樋口隆史（依頼者・利用者の立場） | 目的と対象者を提示し、診断の偏りを指摘。6B・7Bの比較と、8GB→16GBの分担という方向を提案 |
| AIアシスタント | 公式資料の確認、画面とロジックの実装、操作検証、修正、オフライン版生成、非公開ホストへの反映 |
| 実運用する組織 | 端末・モデル・情報の利用可否、業務品質、運用コストを判断。これは開発時点で未実施 |

開発時間の削減率や、AIを使わない開発との生産性比較は測定していません。モデル推論の品質や、休眠PCでの効果が実証された事例とも区別します。

## この記録から得られたこと

操作できる試作品を早く用意すると、利用者が具体的な違和感を指摘できます。その指摘を、変更する仕様と検証する条件へ落とし込むことが、今回の改善につながりました。

GitHub版は現在の実装を独立したスナップショットとして保管します。元のSites用Git履歴の時刻・著者情報を偽装して再構成することはしません。

## README点検時に見つかった再現上の問題

2026年9月20日、AIアシスタントがGitHub掲載版の検証スクリプトを再実行したところ、`tests/diagnosis.cjs`で`TypeError: path.join is not a function`が発生しました。HTTPリクエストのパス文字列を`path`と名付け、Node.jsの`path`モジュールと衝突させていたことが原因です。

文字列の変数名を`pathname`へ変更し、診断・受け渡し・オフライン版の3スクリプトを再実行しました。これは今回AIが発見・修正したテスト用コードの問題です。樋口が当初この不具合を発見したことにはせず、アプリ本体の診断ルールも変更していません。結果と実行環境は[検証記録](VERIFICATION.md)に追記しています。
